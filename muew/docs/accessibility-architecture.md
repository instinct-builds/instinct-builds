# MUEW editor accessibility architecture (0.81.0)

The editor is one shared AppKit NSView (`app/MUEWEditorView.mm`) in both the standalone window and the AU Cocoa view. Most visible controls are drawn into that view; they are not AppKit subviews and do not get accessibility roles automatically. The `NSSearchField` is a real subview with its own field editor, query, focus, and native text actions. Do not replace it with a simulated accessible control. The AU wraps the editor in `MUEWAUEditorContainer_0_66`, but a DAW owns keyboard routing: the AU's `playsNotes()` is false, and no editor accessibility implementation should seize host keys.

## Ownership and phased tree

* Standalone: window > editor > native Search plus virtual browser list when the browser is open. AU: host window > AU Cocoa container/editor > the same native Search and virtual browser list. Hidden browser elements must be absent from children, not merely off-screen.
* Browser pilot: the editor owns a named virtual list of only the currently visible rows. Each row represents one immutable preset slug, has a name, category and position within the current filter, and separately announces proposed and loaded state. The Search field remains native. A row's accessibility press resolves its saved slug against the **current** visible set and refuses to act if it is gone; it never substitutes a row number. Querying, moving accessibility focus and constructing rows must never load a preset or send a note. A deliberate press may load a resolved row. The existing keyboard Return path keeps its own checked cursor semantics. The browser's other custom-drawn parts (bank/type/tag filters, sort headers, stars, save/import/export, loaded-sound details, close) remain mouse-only in this pilot. This is not a claim that the whole browser is accessible.
* Instrument controls beyond browser: header presets/macros, oscillator/unison, filter, modulation matrix, wavetable editor, performance/arp, FX chain/details, output readout and keyboard are drawn and require their own virtual elements, group hierarchy, value units, adjustable actions, focus order and live-state notification strategy. AU parameter automation is not a substitute for labels or actions in the editor. Do not describe the instrument as VoiceOver-ready until those controls are implemented and tested.
* Dialogs: save uses an NSAlert with an NSTextField, and import/export use standard NSOpenPanel/NSSavePanel. Let AppKit expose these native modal trees. Restore focus to a meaningful editor element on dismissal in a later dialog pass; do not attach modal controls to the browser virtual tree.

## State and lifecycle contracts

`visible`, `bscroll`, `filter`, `sortMode`, `currentIndex` and `browserCursorSlug` are the only sources for browser row order and states. Rows are snapshots identified by slug, not persistent objects tied to an index. Rebuild on query/sort/filter/scroll/load, and give only on-screen rows a frame. A retained stale row is inert. Distinguish proposed (amber cursor slug) from loaded (teal currentIndex) in words even when both happen to match. Expose results count and position so the number does not depend on scrolling. A query that removes the cursor clears the proposal; it must not announce or activate a replacement. Any notifications about row creation, selection or value changes must be scoped to this pilot and verified with a client rather than assumed from rendering.

## Proof boundary

The macOS host harness can query the AppKit accessibility objects and call a row's press action through the same process. This tests tree data and action invariants, not actual VoiceOver speech, remote AXUIElement IPC, assistive-technology permission prompts, or use inside Ableton. A full screen-reader pass requires manual VoiceOver in standalone and at least one AU host, including traversal of every control and dialog and focus restoration. Keep those limitations visible in release notes. Apple guidance on custom drawn controls: https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html and https://developer.apple.com/documentation/appkit/nsaccessibilityelement .

## 0.84.0 loaded-sound actions

Bank, Type/Favorites, sort and Close have shared mouse/AX paths and retain their identities across refiltering. Loaded-sound Favorite, five rating buttons, Save, Import and Export now follow that pattern too. Their labels explicitly name the loaded sound, not the proposed row. Detail handles survive refilter and sort, but are replaced on a sound load or changed host recall; retained handles refuse to target the replacement. Closing also invalidates them. Row rating cells and character-tag filters remain mouse-only.

File presses open the existing native AppKit modal dialogs asynchronously so a remote AX call does not block the IPC reply inside a modal loop. The queued launch rechecks its captured epoch. While a dialog is active, AX browser actions cannot load or edit another sound. Cancellation returns keyboard focus to the editor's result list without writing a preset. Tests exercise actual dialog launch/cancel, not a substitute mock. They do not claim full dialog completion, screen-reader focus return/speech or traversal inside a real AU host.
